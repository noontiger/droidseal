# DroidSeal Governance

## Governance model

DroidSeal follows a maintainer-led governance model. The project welcomes public discussion and external contributions, while maintainers retain final responsibility for project direction, security, release quality, and compatibility commitments.

## Maintainer responsibilities

Maintainers are responsible for:

- reviewing and merging pull requests;
- managing releases and signing official artifacts;
- maintaining private security-reporting channels;
- defining supported platforms and versions;
- approving changes to security boundaries;
- maintaining project and release infrastructure;
- enforcing the Code of Conduct;
- documenting major technical decisions whenever practical.

## Decision process

Routine bug fixes, documentation changes, and tests may be approved through normal pull request review.

The following changes should be discussed before implementation:

- changes to the project license or trademark policy;
- new network communication or automatic download behavior;
- plugin or external-protector protocols;
- breaking CLI, output-directory, environment-variable, or report-schema changes;
- new credential-storage mechanisms;
- changes to supported platforms;
- major architectural changes.

Maintainers should seek consensus when practical. When consensus cannot be reached, active maintainers make the final decision and document the reasoning.

## Becoming a maintainer

A contributor may be invited to become a reviewer or maintainer based on sustained high-quality contributions, sound security judgment, constructive participation, reliable review work, and understanding of the project's safety and compatibility requirements.

Maintainer status is granted by the existing maintainers.

## Inactive maintainers

Maintainers who are inactive for an extended period may be moved to emeritus status. Emeritus maintainers retain recognition but are not required for routine decisions.
