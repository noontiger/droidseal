# DroidSeal 开源与商业化实施路线

> 状态：待执行  
> 适用范围：Community 源码仓库、官方 Windows 二进制、npm 发布和未来商业模块  
> 推荐模式：Community 核心完整开源 + 官方免费二进制 + 独立闭源 Pro/Enterprise 模块

## 1. 执行规则

本路线只保留尚未完成的工作，不把“写了代码”视为完成。

1. 严格按任务编号执行，同一时间只允许一个任务处于执行状态。
2. 前置任务未通过验收，不开始依赖它的后续任务。
3. 每项完成后，先把结果、测试命令和迁移说明写入 `CHANGELOG.md` 或发布证据，再从本文删除该任务。
4. “验收标准”必须全部满足；无法自动验证的项目必须留下人工复核记录。
5. 许可证内容是工程控制要求，不代替专业法律意见。

## 2. 当前基线与阻断项

已经具备：

- MIT、贡献指南、DCO、治理、安全披露、行为准则和商标政策；
- Windows x64 单文件二进制和 binary-only npm 包；
- 源码/APK 审计、R8 覆盖、Manifest 归一化、可选 Web JavaScript 与 ARSC 处理、对齐、签名、验证、SBOM 和证据报告；
- 219 项自动化测试通过；
- `bun run release:check` 已确认当前 npm 包不携带项目源码、脚本、source map、APK、签名材料、已知 secret 模式或本机用户路径。

公开前阻断项：

| 编号 | 阻断项 | 风险 |
| --- | --- | --- |
| B-01 | Git 根目录是用户目录，而不是 DroidSeal 目录 | 直接公开可能带入用户目录中的无关文件、隐私或历史 |
| B-02 | 发布检查不证明父仓库完整历史无敏感内容 | 已删除文件或凭据仍可能留在旧提交中 |
| B-03 | Bun/WebKit/TinyCC LGPL 工程材料已完成，但尚无发行方指定法律顾问的书面签核 | 工程控制不能替代对具体发行方式的专业法律意见 |
| B-04 | 尚无 npm Trusted Publishing、provenance、签名 Tag 和 EXE 身份链 | 用户难以验证二进制与公开源码的对应关系 |
| B-05 | 研究性 DEX 写回代码与主线处于同一源码层级 | 用户可能把实验能力误认为生产能力 |
| B-06 | Community 与商业模块没有稳定技术边界 | 容易出现闭源代码混入公共仓库或核心功能被反复搬迁 |

## 3. 固定产品边界

### Community 必须公开

- 当前受支持的审计、证据、误报抑制、报告、SBOM 和修复建议；
- APK/AXML/ARSC/DEX/ELF 只读解析及受支持的确定性后处理；
- R8 构建覆盖、Web JavaScript 发布处理、资源混淆、对齐、签名和验证；
- UI、CLI、公共配置、Finding Code、置信度模型和报告 Schema；
- 构建脚本、发布检查、正例、反例和安全回归测试；
- 公共插件协议和第三方插件所需的最小 SDK；
- 现有研究模块可以公开，但必须位于实验命名空间且默认不可调用。

基础漏洞规则、证据逻辑、误报修复和安全公告不得为了商业化转为付费专属。

### 私有边界

- 客户 APK/AAB、签名密钥、密码、报告、日志和内部样本；
- 客户策略、私有合规规则、私有 SDK 指纹和未公开威胁情报；
- SSO、组织/角色、中央策略、集中报告、审计日志和 SLA 系统；
- 未来成熟的 DEX 抽取/加密、专用加载器、VMP、Native RASP、反 Hook/反注入引擎；
- KMS/HSM/远程签名连接器、许可证服务、计费和支持系统；
- 第三方授权禁止再分发的规则、SDK、二进制和文档。

### 分发层次

| 版本 | 源码 | 价格 | 能力 |
| --- | --- | --- | --- |
| Community | MIT 公开 | 免费 | 当前本地流水线、基础规则、报告、SBOM、公共插件协议 |
| Official Binary | 与 Community 同源 | 免费 | 签名且带 provenance 的 npm/GitHub 便捷安装包 |
| Pro | 独立私有模块 | 付费 | 高级本地插件、专属策略、优先规则更新、专业支持 |
| Enterprise | 独立私有仓库/服务 | 付费 | 组织治理、SSO、集中报告、KMS/HSM、私有部署和 SLA |

## 4. 阶段 0：冻结开源决策

预计投入：0.5—1 个开发日，不含法律复核。

### OS-0001 确认许可证与贡献模式

具体工作：

- 书面确认 Community 继续使用 MIT；
- 明确 MIT 允许复制、修改、分发和销售，商标政策只保护官方身份；
- 确认闭源模块使用独立仓库、包名和商业许可证；
- 决定继续使用 DCO，还是在首个外部贡献前引入 CLA；
- 如果考虑双许可证，必须在接受大量无版权转让的贡献前决定。

交付物与验收：

- `GOVERNANCE.md` 写明 Community/Commercial 决策权；
- `CONTRIBUTING.md` 写明贡献许可证和 DCO/CLA 选择；
- `LICENSE`、贡献说明和 `TRADEMARKS.md` 不冲突；
- 新贡献者能够回答“贡献按什么许可”“能否销售 Fork”“能否使用 DroidSeal 名称”。

### OS-0002 固化功能分层

具体工作：

- 新增 `docs/editions.json`，字段至少包含 `id`、`edition`、`support`、`defaultEnabled`、`dataBoundary`；
- 将所有现有流水线步骤标为 Community；
- 将 DEX 写回、字符串密码计划和注入标为 `experimental`，不得标成已有 Pro 能力；
- README 功能表由相同数据源生成或由测试校验，避免文档与实现漂移。

验收标准：

- 每个 UI 可见能力映射到唯一层级；
- Community 不依赖私有仓库也能构建、测试和运行；
- 计划功能和已交付功能在机器数据与文档中均可区分。

## 5. 阶段 1：建立干净的独立仓库

预计投入：1—2 个开发日。这是所有公开操作的 P0 前置条件。

### OS-0101 建立公开文件白名单导出器

允许迁移：`.github/`、`src/`、`tests/`、`scripts/`、`docs/`、根配置、锁文件和项目拥有的法律/社区文档及 fixture。

禁止迁移：`.git/`、`node_modules/`、`dependencies/`、`dist/`、`*.tgz`、APK/AAB、JKS/keystore、证书、私钥、环境变量、用户报告、设备日志、IDE 缓存、绝对用户路径和父仓库历史。

实现要求：

- 新增只读脚本，按固定白名单导出到新建暂存目录；
- 文件名、扩展名或内容检查失败时整体失败；
- 输出相对路径、大小和 SHA-256 清单；
- 禁止把用户主目录、项目原目录或磁盘根作为导出目标。

验收标准：

- 导出清单所有路径都在白名单内；
- 导出目录没有 `.git`、二进制发布物、用户制品和签名材料；
- 同一提交连续导出两次，清单完全一致。

### OS-0102 初始化独立 Git 仓库

具体工作：

- 在白名单导出的新目录执行 `git init`；
- 首次提交只包含清单确认的文件；
- 不使用 `subtree`、历史过滤或复制父仓库 `.git` 的方式迁移；
- 设置官方 DroidSeal 远程；
- 新仓库确认无误前不删除原工作目录。

验收标准：

```powershell
git rev-parse --show-toplevel
git status --short
git ls-files
git log --all --oneline
```

- Git 根必须是新的 DroidSeal 目录；
- 首次提交后工作树为空；
- tracked 文件与导出清单一致；
- 历史不包含父仓库提交。

### OS-0103 扫描工作树和完整历史

具体工作：

- 保留 `release:check`，增加固定版本和校验和的历史秘密扫描工具；
- 扫描当前树、全部分支、Tag 和提交历史；
- 覆盖私钥、JKS/PKCS12、云密钥、GitHub/npm Token、密码赋值、本机路径和 APK/AAB；
- fixture 只能使用明显无效的模拟值，并逐项记录精确豁免理由；
- 禁止忽略整个目录或文件类型的宽泛豁免。

验收标准：

- 当前树和完整历史均无未解释结果；
- 豁免记录包含规则、路径、理由和复核人；
- CI 对每个新提交运行同样扫描。

## 6. 阶段 2：隔离实验代码并固定公共格式

预计投入：2—4 个开发日。

### OS-0201 建立实验命名空间

具体工作：

- 将 DEX codec/model/writer/string-crypto、AXML writer 和 lossy inject 等研究代码迁入 `src/experimental/`；
- 主流水线不得从 `src/experimental/` 导入；
- 实验测试迁入 `tests/experimental/`，继续执行但单独汇总；
- 新增实验说明，列出支持子集、失败关闭条件、真机门禁缺口和生产禁用原因。

验收标准：

- 静态依赖测试确认 `src/core/pipeline.ts` 到实验目录的导入数为零；
- 默认构建和 npm 二进制不暴露实验命令或 UI；
- 实验测试仍阻断合并，但不会形成生产兼容承诺。

### OS-0202 固化公共 Schema 与兼容政策

具体工作：

- 为 Finding、Evidence、Operation、Report、SBOM 扩展建立版本化 JSON Schema；
- Finding Code 不得静默改义，废弃时保留映射；
- 新增字段默认向后兼容，删除或改义进入主版本升级；
- 每个 Schema 提供最小示例、完整示例和解析测试。

验收标准：

- 当前报告通过 Schema 校验；
- 上一个公开版本 fixture 可被当前解析器读取；
- 不兼容变化会在 CI 中失败。

## 7. 阶段 3：取得 Bun LGPL 组件外部法律签核

工程清单、通知、对应源码、重新链接说明和自动门禁已经完成；本阶段只保留不能由项目代码或 AI 代替的发行方专业法律确认。

### OS-0302 记录发行方指定法律顾问的书面结论

- 让熟悉 LGPL 的法律顾问按实际 npm/GitHub Release 分发结构复核 `licenses/Bun-LGPL-RELINKING.md`、Bun 官方许可声明、固定 WebKit/TinyCC 源码及用户修改/重新链接路径；
- 记录复核人、日期、适用的 Bun 版本、WebKit/TinyCC 提交、分发渠道、结论和必须保留的材料；
- 若现有静态可执行文件方案不被接受，改用经确认的动态链接/可重新链接结构或停止分发该二进制，不以单纯附带 LICENSE 代替结论。

验收标准：

- 书面记录明确覆盖 Bun 1.3.14、WebKit `5488984d20e0dbfe4be2c3ba8fb18eb81a5e0e8b`、TinyCC `12882eee073cfe5c7621bcfadf679e1372d4537b` 和 Windows x64 npm/GitHub Release；
- 结论列明用户获得对应源码、修改、重新链接和运行修改版本所需的材料及步骤；
- 法律顾问要求的条件已进入发布清单与自动门禁，Bun/WebKit/TinyCC 版本变化触发重新复核。

## 8. 阶段 4：公开仓库安全与质量门禁

预计投入：3—5 个开发日。

### OS-0401 强化发布检查

在现有 `release:check` 增加：

- Git 根必须等于项目目录；
- 发布提交必须是干净工作树和可追溯 Tag；
- npm 文件与允许清单完全一致；
- EXE、外置资产、tarball、SBOM 和许可证分别记录 SHA-256；
- 构建元数据记录源码提交、工具版本、锁文件哈希和 CI run；
- 发布包不得出现临时目录、绝对源码路径和 sourcemap 引用。

验收标准：

- 每项至少有一个自动化失败负例；
- 本地与 GitHub Actions 判定一致；
- 门禁失败时不创建 Tag、不发 npm、不上传 Release。

### OS-0402 建立误报控制准入规则

每个新增 Finding 必须有：

- 稳定 Code、严重度、置信度和证据来源；
- 至少一个真实结构正例和两个相似但安全的反例；
- 源码与 APK/DEX 模式能力差异；
- 扫描上限、截断、失败降级和修复建议；
- 动态字符串、反射、资源引用或混淆无法确认时的降置信度路径。

验收标准：

- 缺少反例的规则不能合并；
- 单个常见类名、API 名或算法名不能直接形成漏洞结论；
- 发布报告统计置信度和规则变化，能够观察误报漂移。

### OS-0403 配置 GitHub 保护

- 主分支禁止直接推送，必须经 Pull Request；
- CI、DCO、秘密扫描、依赖审查和发布检查设为 Required Checks；
- `CODEOWNERS` 保护工作流、发布、许可证、签名和策略代码；
- 开启私密漏洞报告、Dependabot、安全公告和适用的静态分析；
- 工作流权限默认只读，发布 Job 单独申请最小权限。

验收标准：

- 普通贡献者不能绕过 Required Checks；
- Security 页面能私密报告漏洞且维护者收到测试通知；
- Fork PR 无法读取发布凭据。

## 9. 阶段 5：可验证的官方发布链

预计投入：2—4 个开发日，不含代码签名证书申请时间。

### OS-0501 建立版本与候选流程

- 首次公开版本使用 `0.1.0-beta.1` 一类预发布版本；
- `package.json`、构建元数据、Tag 和报告版本一致；
- 候选先进入 GitHub prerelease，通过干净机器安装后再提升；
- npm 使用 `beta` 和 `latest` dist-tag，测试版不得覆盖 `latest`；
- 每个版本包含变更、限制、升级、回退和支持范围。

验收标准：

- 版本不一致时 CI 失败；
- 全新 Windows 用户目录安装后 `droidseal --version` 正常；
- 回退版本无需删除用户项目或全局配置。

### OS-0502 配置 npm Trusted Publishing 与 provenance

- npm 绑定精确 GitHub 组织、仓库、工作流和环境；
- 使用 OIDC，不保存长期 `NPM_TOKEN`；
- GitHub 托管 runner 仅给发布 Job 最小 `id-token: write`；
- `package.json.repository` 与真实公开仓库大小写一致；
- 发布后验证 provenance 的源码提交和构建工作流。

验收标准：

- GitHub Secrets 没有长期 npm Token；
- npm 页面显示有效 provenance；
- 非授权工作流或错误仓库无法发布。

### OS-0503 签名和归档制品

- 使用受控 Windows 代码签名证书给 EXE 签名并加可信时间戳；
- Tag 和 Release 由维护者签名；
- Release 提供 EXE、tarball、SHA-256、SBOM、许可证通知和构建元数据；
- 私钥只存在于受控签名服务/HSM 或 CI 机密边界；
- 签名后重新验证哈希、PE 签名和启动冒烟。

验收标准：

- Windows 签名和时间戳有效；
- Release 哈希与 npm 实际下载内容一致；
- 任意签名后修改都会被验证发现。

## 10. 阶段 6：公开运营

预计投入：2—3 个开发日完成设置，之后持续维护。

### OS-0601 建立贡献与支持边界

- 明确 Issue 分类、复现信息、脱敏和支持范围；
- 普通问题、误报和安全漏洞使用不同入口；
- Alpha 只支持最新版，上一个版本尽力支持；
- 每个版本指定 Release Owner 和 Reviewer；
- 没有能力兑现时调整承诺，不设置虚假 SLA。

验收标准：

- 模板禁止上传真实密钥和未脱敏 APK；
- 安全问题不会被引导到公开 Issue；
- 发布清单可追溯负责人和复核人。

### OS-0602 建立公开路线与决策记录

- 公共路线只包含 Community 能力；
- Schema、插件 API、许可证和安全边界变化采用轻量 RFC/ADR；
- 客户身份、私有需求和商业日期不进入公共路线；
- 每季度清理失效规划，研究方向不能伪装为交付承诺。

验收标准：

- 重大兼容变化均有决策记录；
- 公开路线不要求访问私有仓库；
- README 只描述当前能力，未来能力明确标记为计划。

## 11. 阶段 7：Community/Commercial 技术隔离

预计投入：1—2 周完成公共协议和样例；商业实现另行估算。

### OS-0701 设计进程外插件协议

优先使用版本化 JSON-RPC/JSONL over stdio，不让 Community 直接导入闭源 TypeScript：

- `handshake`：协议、插件、发行者、能力和许可证状态；
- `audit`：只读输入，返回公共 Finding/Evidence；
- `transform`：接收隔离副本，返回新制品及输入/输出哈希；
- `attest`：返回插件版本、策略和构建证据；
- `cancel`/`timeout`：中止与确定性超时；
- capability 区分 `read-apk`、`write-apk`、`network`、`signing-request`。

安全约束：

- 插件不能读取 Community 进程内密码；
- 默认无网络，联网插件必须显式提示；
- 修改型插件只操作隔离副本，失败保留上一步制品；
- 插件输出仍经 DroidSeal 对齐、签名和最终验证；
- 插件崩溃不得覆盖用户源码或原 APK。

验收标准：

- 公共样例能完成一次只读审计和一次隔离变换；
- 版本不匹配、超时、哈希错误和路径越界均有失败测试；
- 不安装私有插件时 Community 全部现有能力可用。

### OS-0702 创建私有仓库边界

```text
droidseal/                    # MIT Community
droidseal-plugin-sdk/         # MIT 公共协议、Schema、示例
droidseal-pro-plugins/         # 私有高级本地插件
droidseal-enterprise/          # 私有控制面、SSO、报告、策略
droidseal-release-private/     # 私有签名和商业发布自动化
```

实施要求：

- 私有仓库不能成为 Community 构建、测试或安装依赖；
- 公共仓库不保存商业许可证验证私钥；
- 私有包使用不同包名、版本和许可证；
- 公共 API 先完成 Community RFC，再更新私有实现；
- 自动阻止客户域名、私有仓库 URL 和商业密钥进入公共仓库。

验收标准：

- 无私有权限的干净环境可完整构建、测试和发布 Community；
- 删除商业插件后，Community 能准确报告未执行的可选能力；
- 任一仓库泄漏都不会同时暴露客户签名私钥和商业许可私钥。

## 12. 阶段 8：商业 MVP

预计投入：Pro 4—8 周；Enterprise 8—16 周。按单人连续开发估算，不含法务、销售和客户等待时间。

### OS-0801 Pro MVP

首版只选择一个可独立验证的付费价值，推荐顺序：

1. 私有组织策略包和签名更新；
2. CI 策略门禁、基线差异和误报审批；
3. KMS/HSM/远程签名连接器；
4. 设备矩阵成熟后再做高级 Native/DEX 防护插件。

必须具备：

- 离线许可证宽限和清晰失效行为；
- 失效只关闭付费能力，不破坏 Community 输出；
- 记录插件版本、输入/输出哈希和策略 ID；
- 明确 Android/AGP/JDK/设备矩阵；
- 独立回滚开关和兼容测试。

验收标准：

- 付费价值可用客观输出或节省成本验证；
- 基础漏洞修复、误报修复和安全公告不设为付费专属；
- 商业插件失败可安全回退到 Community 流水线。

### OS-0802 Enterprise MVP

建议范围：组织、角色、SSO、项目、策略版本、审计日志、私有部署、报告/策略签名、保留删除机制、GitHub/GitLab/Jenkins 集成和 SLA。

数据边界：只上传用户选择的报告摘要，默认不上传 APK、源码和密钥；客户可完全关闭遥测并继续使用本地核心。

验收标准：

- 数据流图覆盖每类数据的产生、传输、存储和删除；
- 租户隔离、越权、审计完整性和备份恢复有自动化测试；
- 私有部署不依赖维护者能够访问客户制品。

## 13. 阶段 9：1.0 发布门槛

满足全部条件后才能从 `0.x` 提升到 `1.0.0`。

### OS-0901 兼容性与质量

- 报告 Schema 和插件协议有稳定版本及弃用政策；
- Windows、Android 工具链发现和错误恢复持续测试；
- 源码项目、普通 APK、混合 APK 和异常 APK fixture 全部通过；
- 真机矩阵覆盖主要 Android 版本、ABI、签名方案和至少两个厂商 ROM；
- 连续两个公开版本没有未解决 P0/P1 发布缺陷；
- 误报回归集版本、来源和趋势可追踪。

### OS-0902 安全与供应链

- npm provenance、Tag/EXE 签名、SBOM、许可证和哈希均自动生成及验证；
- 私密漏洞报告、修复、公告和 CVE 流程至少演练一次；
- 发布者强制多因素认证，工作流无长期 Token；
- Community 能从干净公开源码构建功能等价制品；
- 外部安全审查高危问题全部关闭或有公开风险说明。

### OS-0903 运营

- 至少两名能够发布和修复安全问题的维护者，或公开单维护者风险；
- 支持范围、响应边界、备份负责人和中止发布流程已文档化；
- Community 与商业版功能表、数据边界和支持承诺一致；
- 商业压力不得绕过 Community 安全门禁或长期延后基础修复。

## 14. 严格执行顺序

```text
许可证/贡献决策
  -> 功能分层
  -> 白名单导出
  -> 独立 Git 仓库
  -> 全历史秘密扫描
  -> 实验代码隔离
  -> Bun LGPL 组件外部法律签核
  -> GitHub/CI 安全门禁
  -> npm provenance 与签名发布
  -> Community Beta
  -> 公共插件协议
  -> 私有 Pro/Enterprise 仓库
  -> 商业 MVP
  -> 1.0 门槛
```

第一阶段公开目标是可信、可审计、可追溯来源的 Community Beta，不是立即推出收费壳。只有 Community 发布链和插件隔离稳定后，才能对外承诺商业防护能力。
